## How a judge uses this manifest

1. Take the filled manifest (path: pending). For each shipped file, compute its sha256 and compare with the manifest field. A mismatch means the file is not the recorded evidence. `command: pending`
2. Replay the offline check: re-score the stored generations with the dev-only Inspect task (`glimmer_ifevalg`) using the pinned dataset hash. The recorded agreement is 300 of 300 prompts on pass-all, constraint fraction and truncation (`REPRODUCE.md` step (b)). `command: pending`
3. Rebuild the report tables from the ledger export and compare with `REPORT.md` section 12. Aggregates must match exactly; cells the ledger cannot fill read "not in final facts supplied" or `not run` as section 12 marks them, and failed trials must never appear as 0%. `command: pending`
4. Check the Muse-authored files against provenance: for each file listed in `submission-pack/provenance/starter-author/muse_authored_files.sha256` and `submission-pack/provenance/pack-writer/muse_authored_files.sha256`, compute its sha256 and compare; then read the session row in `PROVENANCE.md` (prompt file, prompt sha256, model, Muse Code version, events file, host, started, finished, usage, exit code) against the prompt and event log stored in the same folder. A file that appears in neither listing is not evidenced as Muse-authored, wherever it sits. `command: pending`
5. For any filled training row, follow its data-origin hash record: the train file, samples file, data file and verifier module it names must be the files the row trained on, and a refusal must be recorded where data was refused. Remember the limit while doing this: the check cannot detect a recipe that forges its own samples file, so this step audits the trail; it does not certify origin by itself. `command: pending`
6. Confirm what is absent: no selection or test rows, no raw private scorer logs, no keys. An evidence bundle that contains those has failed its own rules, and the fix is removal before publication, not a footnote.
